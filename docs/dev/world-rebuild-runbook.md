# World Rebuild Runbook

This runbook covers the campaign to rebuild the entire XEarthLayer regional
scenery library: retiring every package published so far and replacing it with
thirteen new ones, published through a staging channel and promoted to stable
one region at a time.

It is the campaign, not the mechanics. The per region publishing procedure
lives in [Publishing Packages via GitHub Releases](github-releases-publishing.md)
and is not repeated here. What follows is the order the regions go in, the
decisions that were already made so they do not get made again halfway through,
and the preconditions that are easy to get wrong.

## Why Rebuild

Three changes arrive together, and each of them needs the packages regenerated
rather than patched:

- **New regional partitioning.** The old regions were continent sized. A user
  who wanted the western United States had to take the whole of North America.
- **Smaller packages.** Partitioning finer is what makes the library usable on
  a machine that cannot spare hundreds of gigabytes for scenery.
- **7z compressed DSF files.** Every DSF is now written as a single entry 7z
  container, which X-Plane decodes natively. See
  [Package Publisher Design](package-publisher-design.md) for the format and
  why the dictionary size is what it is.

The new packages start at version `0.1.0`. They are new packages under new
region codes, not new versions of the old ones, so their version history starts
fresh.

## Region Naming

`<CONTINENT>-<TERRITORIES>`, uppercase, hyphen separated, where the descriptor
names the dominant territories the region covers:

```
NA-USA-MX-CENTRAL
NA-CANADA-GREENLAND
```

The lowercase form is both the CLI argument and the Custom Scenery folder name
that users end up with:

```
xearthlayer-publish add --region na-usa-mx-central --type ortho ...
  -> packages/zzXEL_na-usa-mx-central_ortho
  -> Custom Scenery/zzXEL_na-usa-mx-central_ortho
```

These descriptive codes replace the older short ones (`NA`, `EU2`, `AS1`) as
each region is rebuilt, which means the library is mixed for the duration of
the campaign: some entries carry old codes and some carry new ones. That is
expected and is why the old and new regions coexist in
`region_metadata.json`, linked by `supersedes` and `replaced_by`.

Only the two North American codes above are settled. The remaining eleven are
named as their regions come up, because the naming follows from what the merged
source actually covers.

## Preparing the Source

Each region is generated by several Ortho4XP instances running in parallel.
Merge those instance trees into one source tree, placed in the repository's own
`staging/` directory, which `publish init` creates for exactly this purpose:

```
<repo>/staging/na-usa-mx-central/
```

Keeping the merge inside the repository keeps the working set in one place, so
it is obvious what can be deleted once the package is built and there is no
stray tree left behind on another volume.

The merge policy, the transfer filter, and the trap that catches people
checking a merged tree by eye are documented in
[Merging Multiple Ortho4XP Instances](github-releases-publishing.md#merging-multiple-ortho4xp-instances).
Read that before starting a transfer. The short version, because getting it
wrong is silent: **every PNG under a tile's `textures/` directory is a water
mask**, named `{x}_{y}_ZL{n}.png` with nothing in the name marking it as a
mask, so a filter that looks for a `_mask` or `_sea` suffix matches nothing and
produces a package with no water boundaries.

## The Per Region Loop

1. Merge the instance trees into `<repo>/staging/<region>/`.
2. `publish scan --source <repo>/staging/<region>` and read the tile count and
   zoom level report.
3. `publish add --source <repo>/staging/<region> --region <region> --type ortho`,
   then the same against the overlay source tree with `--type overlay`.
4. `publish gaps --region <region> --type ortho`. Only if it reports zero gaps,
   `publish dedupe`.
5. `publish build` for both types.
6. Verify locally, over a local HTTP server (below).
7. Publish the GitHub release, configure the real URLs (a second `publish urls`
   run against the real GitHub base URL, following the `localhost` one used
   for local verification in step 6), upload metadata, and `publish release`
   for both types. This is the procedure in
   [Publishing Packages via GitHub Releases](github-releases-publishing.md).
8. Commit the library index and `region_metadata.json` on the `staging` branch
   and push.
9. Test the staging channel end to end as a user would.
10. Open the promotion pull request from `staging` to `main`.
11. After it merges, retire the region it supersedes with `publish delete`.

## Preconditions That Are Easy To Get Wrong

**Do not pass `--dedupe` to `publish add`.** Deduplication decides whether to
remove a lower zoom tile by asking whether every higher zoom child covering it
exists, and `--dedupe` asks that question the instant the tiles have been
copied, against whatever is in the package at that moment. If the package is
built up from more than one pass, which is the normal case when a source turns
out to be incomplete and tiles are added later, that question was answered on a
subset: tiles kept because their children were missing stay kept, and the
second pass does not revisit them. Deduplicate once, as its own step, when the
package holds everything it is going to hold.

**Run `gaps` before `dedupe`, and only dedupe if it reports zero gaps.**
Removing a lower zoom parent whose higher zoom children are incomplete leaves
the uncovered part of that parent with no texture at all: untextured terrain in
the sim, not merely lower detail. `dedupe` does guard against exactly this: it
skips any overlap whose coverage is not complete, so the worst outcome will not
happen by accident. The guard is silent, though, and says nothing about
coverage you meant to ship and do not have. `gaps` is what tells you that,
which is why it goes first even though the guard exists.

**Upload the package metadata after running `urls`, never before.** `urls`
rewrites the metadata file with the download URLs, and `release` checksums that
file as it is on disk at the time. Upload it first and the published metadata
is the version without URLs, while the library index advertises a checksum for
the version with them. The install fails a checksum comparison the user has no
way to explain.

**Put the merged source in `<repo>/staging/`,** not on a scratch volume
elsewhere. See above.

**Retire the old region after promotion, not before.** Covered below.

## Local Verification Before Publishing

Verify a built package by installing it the way a user would, before any of it
reaches GitHub. That means serving the repository over HTTP:

```bash
# In the repository root
python3 -m http.server 8000

# In another shell
xearthlayer packages install na-usa-mx-central \
  --library-url http://localhost:8000/xearthlayer_package_library.txt
```

A `file://` URL will not work. The package manager fetches the library index
and the package metadata through `ManagerClient::fetch_text`, which is a plain
reqwest HTTP call with no file scheme support, so a `file://` library URL fails
at the request rather than falling back to reading the path. A throwaway HTTP
server is the shortest route to exercising the real code path.

There is a sequencing trap here worth stating plainly, because it is the same
trap as "upload metadata after `urls`" wearing different clothes. A local test
needs `publish urls` pointed at `http://localhost:8000/...` so the package
metadata advertises URLs the local server can serve. Those URLs are then wrong
for publication. **Run `urls` a second time against the real GitHub base URL
before uploading the metadata file**, or you will publish a package whose parts
point at a laptop.

## Publishing to Staging

The staging channel, the reasons it is a branch rather than a second filename,
and how a tester points at it are documented in
[Staging Channel](github-releases-publishing.md#staging-channel).

Two things about it matter to this campaign in particular. Users on the stable
channel see nothing at all while a region is in staging, which is what makes it
safe to run a rebuild of this size over an extended period without disturbing
anyone. And release assets are not branch scoped, so the archives a tester
downloaded from staging are byte for byte the archives a stable user downloads
after promotion: promotion cannot introduce a difference between what was
tested and what shipped.

Before opening the promotion pull request, `region_metadata.json` on the
`staging` branch should carry, for the new region, `status: "staging"` and a
`supersedes` array naming the region or regions it replaces. The old region
gains `status: "deprecated"` and a matching `replaced_by`. The new region's
`status` becomes `stable` as part of the promotion.

## Promotion and Retirement

Promotion is a pull request from `staging` to `main`. Merging it is what
releases the region to everyone, because the push to `main` is what triggers
the website sync.

**Retire the superseded region only after that pull request has merged.** Users
on the stable channel are installing from the old package right up to the
moment the new index reaches them. Delete it first and the stable library
offers nothing at all for that part of the world until the promotion lands: a
user who runs `packages check` in that window sees the old region disappear
with no replacement. Deleting afterwards means the two overlap instead, which
costs nothing.

```bash
# Look first: this deletes nothing
xearthlayer-publish delete --region na --dry-run

# Then retire it, both package types
xearthlayer-publish delete --region na
```

This reclaims local disk in the working repository, which is a real motivation
at this scale: the old world occupies 895 GB there. It removes the library
index entry, the package working directory and the built archives. The index
edit is local, like any other, so commit and push it on `main` afterwards.

It does **not** remove the GitHub release assets, deliberately. Those URLs are
what an install already in progress is still fetching from, and they cost
nothing to leave in place. Take the old releases down as a separate, manual
step once you are satisfied nothing is installing from them:

```bash
gh release delete na-v0.4.0 --repo samsoir/xearthlayer-regional-scenery
```
